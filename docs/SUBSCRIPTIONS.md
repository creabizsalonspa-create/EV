## Workflow and endpoints

- `GET commercial/plans`: paginated available audience plans; administrators also see retired versions. Each immutable version carries `code`, `version`, `name`, `audience`, `currency`, `minor_units`, integer `price_minor`, `tax_bps`, `interval` (`month`/`year`), and typed boolean/integer `entitlements`.
- `POST commercial/plans` (admin): publish a new version with the fields above, omitting generated version/id. Currency precision must already be configured. Reusing a code cannot change audience/currency/precision. Historical prices and entitlements cannot be edited. A newly published version does not silently change existing subscriptions; select the version in a plan-change request.
- `PATCH commercial/plans/{id}/availability` (admin), `{available: false}`: stop new enrollment/plan changes; existing contractual renewals remain intact.
- `POST commercial/subscriptions`, `{plan_id,idempotency_key}`: create one pending subscription and its first immutable cycle invoice. A user may have only one non-cancelled subscription. No features are granted until the invoice is paid.
- `GET commercial/subscriptions`: paginated own subscriptions, or all for admins.
- `GET commercial/subscriptions/{id}`: shared detailed source of truth: `subscription`, `plan`, immutable `invoices` (including paid flag), `entitlements`, `entitlements_active`, `ledger_balanced`, `billing_provider: MOCK_PROVIDER`, `real_payment_processed: false`.
- `POST commercial/subscriptions/{id}/mock-payment`, `{invoice_id,outcome:succeeded|failed,idempotency_key}`: explicit non-production-only simulated billing. A failed attempt becomes past due, grants no unpaid features, remains in immutable history, and may be retried with a new key. A successful attempt inserts one immutable full-amount receipt and balanced journal; duplicate keys are replayed and conflicting payloads return 409. An invoice cannot receive a second receipt. Raw cards and payment tokens are never accepted here. Production returns 503.
- `POST commercial/subscriptions/{id}/change`, `{action,plan_id?,idempotency_key}`: `change_plan` schedules an available same-currency plan version for the next cycle; both upgrades and downgrades take effect at the renewal boundary, with **no implicit proration or immediate feature grant**. `cancel_at_period_end` retains the already paid entitlement period; `resume` removes a scheduled cancellation only while the paid period remains current; `cancel_now` immediately revokes entitlements. Cancellation does not manufacture a refund or erase existing financial records.
- `POST commercial/subscriptions/{id}/renew`: issue a due cycle invoice exactly once or expire a scheduled cancellation. It never captures funds. The next-cycle entitlements are granted only after its full receipt. Renewing early does nothing. After expiry, entitlement checks fail even if a worker was delayed.
- `GET commercial/subscriptions/{id}/events`: paginated immutable actions/failure history, without internal idempotency fingerprints.

Run `php artisan commercial:renew-subscriptions` from the application scheduler at a chosen operational frequency. It locks and rechecks each due subscription and does not collect payments. Scheduling/deployment itself must be verified in the target environment. Periods retain the original calendar anniversary through short months/leap years; changing monthly/yearly cadence resets its anchor at the next boundary. Delayed unpaid renewals do not move the contractual invoice period forward; recovery can require paying subsequent overdue cycles or cancelling/re-enrolling under the agreed policy.

## Financial integrity and integration limitations

Amounts are integer minor units, tax rounds through the shared `Money` helper, and each invoice snapshots tax, currency precision, plan version and entitlements. Immutable database triggers protect plan versions, invoices, receipts, event history and subscription ledger rows in SQLite and PostgreSQL. Invoices debit subscription receivable and credit revenue/tax; receipts debit explicitly labeled mock cash and credit receivable. Unique subscription-cycle and invoice-receipt constraints prevent duplicate billing. PostgreSQL row locks serialize enrollment on the account, modifications on the subscription, and actor-scoped request keys; catalog publication uses a shared regional configuration lock.

The shared `PaymentProvider` is now connected to subscription invoices through `SubscriptionGateway`. Non-production `mock` and `stripe_test` providers share the same immutable subscription receipt/journal and entitlement activation boundary. Authorization alone and client payment-success assertions never activate a subscription. Confirmed server captures and authenticated final Stripe test events may settle an exact next-cycle invoice. Gateway captures cannot bypass a prior manual receipt, and manual mock settlement/cancel-now is blocked while an unresolved gateway checkout exists. Provider capture identity remains stable across HTTP timeouts and changed client retry keys.

The Stripe test adapter has been tested with faked HTTP contracts, **not an actual merchant sandbox account**. External activation, valid PaymentMethods, provider credentials, signed callback delivery and real sandbox evidence remain external validation gates. SCA/3DS reports `action_required` without leaking client secrets; a hosted PSP SDK completion flow is still required. Subscriptions do not automatically charge saved mandates/cards; due renewals issue invoices and require an explicit authorized checkout. Off-session mandates/retries/dunning scheduling remain unfinished. Provider-backed subscription refunds and immutable credit notes are now documented in [SUBSCRIPTION_CREDITS.md](SUBSCRIPTION_CREDITS.md); they do not enable production money movement.

Subscription financial documents use `MOCK-SUB-*` numbering. They are not legally approved tax invoices. Final regional tax treatments, tax registration details, commercial terms, refund/proration policy, merchant activation, operational scheduler, real device/mobile consuming screens and external PSP testing remain release gates. Actual domain features must enforce entitlement decisions server-side; the subscription service returning a flag alone does not gate all unrelated modules.

## Subscription gateway API

Mount authenticated `routes/subscription_gateway.php` in both existing client API groups. Mount stateless `routes/subscription_webhooks.php` in `routes/api.php` outside user authentication; signatures are mandatory. No subscription gateway endpoint accepts a client assertion that funds were captured.

- `POST commercial/subscriptions/{subscription}/checkouts`, `{invoice_id,idempotency_key}`: owner-only, next unpaid cycle, positive full amount fixed from immutable invoice. One unresolved checkout per invoice. Returns a checkout row with `id`, `subscription_id`, `invoice_id`, `provider`, `currency`, `amount_minor`, `status`, `failure_code`, `authorization_expires_at`. A failed/cancelled checkout may be replaced; an uncertain authorized checkout must first be retried/reconciled/cancelled.
- `GET commercial/subscription-checkouts`: own paginated records, or all for administrators.
- `POST commercial/subscription-checkouts/{id}/authorize`, `{token,idempotency_key}`: only opaque provider-owned `pm_*` references with `stripe_test`, or explicit `mock_success`/`mock_decline` with mock. Never raw PAN/CVV. Returns `authorized`, `failed` or `action_required`; none grants entitlements.
- `POST commercial/subscription-checkouts/{id}/capture`, `{idempotency_key}`: full server-confirmed capture creates exactly one immutable receipt/payment journal and activates invoice-snapshot entitlements. Same checkout capture replays return the committed status. All provider operations are disabled in production.
- `POST commercial/subscription-checkouts/{id}/cancel`, `{idempotency_key}`: cancel pending or confirmed uncaptured provider authorization before abandoning a subscription. No refund is manufactured by cancellation.
- `GET commercial/subscription-checkouts/{id}/reconciliation`: `{checkout,receipt,observation,matched,evidence,external_provider_verified:false,real_payment_processed:false}`. Stripe test inspection compares currency/capture/refund observations with the immutable receipt; unresolved/unexpected refunds require operator investigation.
- `POST /api/subscription-payments/stripe-test/webhook`: raw Stripe test event with timestamped `Stripe-Signature`, shared test signing secret and 300-second freshness. Supported events: `payment_intent.amount_capturable_updated`, `payment_intent.payment_failed`, `payment_intent.succeeded`. Correlation uses the provider payment id or original `metadata.creabiz_checkout` generated by the shared adapter. Event identity and raw-body fingerprint are immutable; exact duplicates acknowledge, conflicts reject, signed but mismatched amount/currency/live-mode payloads never create receipts. Final capture events recover a successful server-side capture even when its HTTP response was lost. Older authorization/failure events never downgrade captured checkouts. Unknown event types are acknowledged as ignored.

Subscription detail now returns `receipts`, with each receipt's explicit evidence, and `billing_provider` reflects the most recent receipt evidence (`MOCK_PROVIDER` or `STRIPE_TEST_CONTRACT`). Legacy mock cycle invoice numbering/evidence remains unchanged and must never be presented as a legal tax invoice. Stripe test contracts do not mark real money or live credentials as enabled.

`SubscriptionGatewayTest` adds HTTP-faked authorization/capture/replay, signed webhook recovery, malformed/stale/signature/amount/currency/live-mode rejection, declines/SCA states, owner privacy, unresolved-gateway/manual-settlement guards, stable provider keys on uncertain response, reconciliation mismatch and production fail-closed checks.
