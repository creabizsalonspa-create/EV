# Agent 10 — one private, source-bound customer demo evidence packet

The EV platform's local-only customer demonstration has **three different verification phases**. This tool consolidates their sanitized, owner-only reports into one delivery packet **without accessing any charger, database, PSP, external API or production deployment**.

This is a source-binding and consistency check, **not a cryptographic attestation or a customer acceptance signature**. It must never be presented as successful physical charging or real payment integration.

## Operator sequence

All commands must run on an **authorized isolated local lab**. The fixture must have been generated by the canonical `scripts/client-demo prepare` workflow; its private `access.json` must remain unchanged for the entire demonstration. The local Laravel HTTP service is loopback `127.0.0.1:8000`; no public stage or hardware is contacted by these inspection tools.

Prepare a new owner-only evidence directory (`umask 077`, `chmod 700`). Replace `EXACT_RUN` with the eight-hex run directory and use **unique filenames for each execution**, since evidence files cannot be overwritten.

### Phase 1 — before the demonstration

```sh
node scripts/client-demo-readiness.cjs \
  --manifest artifacts/client-demo/EXACT_RUN/access.json \
  --output artifacts/client-demo/private-evidence/ready-UNIQUE.json
```

This requires both owned OCPP 1.6 and 2.0.1 **simulator processes** to be idle and recent, checks both synthetic stations appear in discovery without physical availability claims, and authenticates the synthetic customer, vendor and Admin for read-only vehicle/reservation/RBAC checks. Real chargers are not started or stopped by this inspection.

### Phase 2 — after the separately authorized *synthetic* charging demonstration

```sh
node scripts/client-demo-session-evidence.cjs \
  --manifest artifacts/client-demo/EXACT_RUN/access.json \
  --output artifacts/client-demo/private-evidence/complete-UNIQUE.json
```

This checks two independently completed *source-linked* simulated CSMS sessions with positive synthetic energy, uniquely owned reservations, matching simulated invoices, no recorded paid/refunded amount and successful customer logout. It does not generate a reservation, source event, financial journal or charging command.

### Phase 3 — independent customer/vendor/Admin finance review

```sh
node scripts/client-demo-ledger-audit.cjs \
  --manifest artifacts/client-demo/EXACT_RUN/access.json \
  --output artifacts/client-demo/private-evidence/ledger-UNIQUE.json
```

This verifies customer 403 denial on private finance journals and vendor/Admin access to two balanced mock-invoice postings. It checks exact receivable/payable/commission/tax entries and forbids unknown cash or duplicate entries. It never performs payment, settlement or refunds.

### Final — bundle the three exact evidence snapshots

```sh
node scripts/client-demo-delivery-packet.cjs \
  --manifest artifacts/client-demo/EXACT_RUN/access.json \
  --readiness artifacts/client-demo/private-evidence/ready-UNIQUE.json \
  --completion artifacts/client-demo/private-evidence/complete-UNIQUE.json \
  --ledger artifacts/client-demo/private-evidence/ledger-UNIQUE.json \
  --output artifacts/client-demo/private-evidence/delivery-packet-UNIQUE.json
```

The packet checker requires each input file and its parent directory to be private (0600 file / 0700 directory), rejects symlinks, oversized or sensitive raw fields and mismatched stage schemas. All three files must contain a **SHA-256 of the exact same private `access.json` bytes**. It verifies that preparation, source completion and finance review happened in order, that the entire demonstration evidence period is no longer than 24 hours, and the last evidence is not more than 72 hours old or materially in the future.

It creates a new owner-only, non-overwriting delivery packet with **only** the source fixture hash, the SHA-256 hashes of the three supporting report files, their three verified phases and explicit `false` values for real charging, real money, live OCPI, payment provider verification, signed source attestation, production acceptance and customer contractual acceptance. The packet contains **no** raw passwords, emails, private invoice or session IDs, cookies, authorization tokens, booking details or invoice amounts.

### Limitations and ownership

An ordinary SHA-256 digest binds the files together but **does not prove who created or signed them**, and a synthetic demonstration cannot prove real Teltonika hardware, OCPI partner acceptance, real billing, payment processing, production release or commercial customer sign-off. All those remain separate requirements. Agent 4 coordinates the final integration, Agent 9 conducts independent QA, and real credentials/charging/network operations require separate authorization.
