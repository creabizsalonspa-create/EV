# Native source-registration observations —21 November2026

Customer/vendor Flutter inventory now opens a read-only source-registration screen for owned `direct_unverified` OCPP1.6/2.0.1 chargers. It consumes Agent1's canonical `GET vendor-ops/companies/{company}/chargers/{charger}/source-registration` contract. Preparation and registration remain authorized Admin web actions. This screen sends only GET, never prepares identities, retries registration, enables credentials, starts charging or changes financial records.

The typed projection distinguishes not-prepared, prepared, registration-in-progress, authenticated source-record readback and requires-inspection states. A historical registration receipt with a mismatched current inventory/source configuration is explicitly flagged for authorized inspection. Every response must preserve source-snapshot/no-live-connection/no-hardware-verification/no-command/no-charging-capability/no-automatic-retry evidence. Unexpected state, identity, timestamp or capability fields fail closed. Source verification time is shown as explicit UTC; it never becomes live availability.

Private snapshots clear on refresh, background, disposal, inventory change and session transition. Foreground return requires an explicit refresh. Real owned401 handling uses the canonical API expiry signal; delayed/background/new-account responses cannot expire a later actor or restore a private snapshot. English/Arabic use the existing themes, localization direction and accessible action/error labels.

Backend implementation and source-registration acceptance belong to Agent1. This native consumer is an integration dependency, not independent proof that source registration, a physical charger, live connection, production deployment or all of original5.2.6 is accepted. The existing company/site/catalog link must identify an owned direct station; simulator/discovery/partner chargers do not expose this new native action. No original whole-atom credit is requested for the read-only component alone.
