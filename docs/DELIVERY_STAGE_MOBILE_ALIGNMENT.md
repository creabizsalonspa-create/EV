# Agent 10 — private staging and mobile developer source-alignment gate

This is an **offline, read-only evidence comparison** plus a new owner-only JSON summary. It must not be used as customer contractual sign-off, actual mobile store release, real charging, payment provider or production acceptance.

## Purpose and dependencies

A successful development-only Android/iOS package can reference one Git commit while a supposedly ready staging installation references **another**. Independent success of both checks would mislead a customer about which software was demonstrated.

This tool fails closed unless the **same exact 40-character Git source SHA** is supported by BOTH:
- Agent 10's PR #66 staging-live-source-acceptance.cjs private, source-labeled, five-container, seven-route HTTPS report, including all runtime/lock/stable-environment checks; and
- PR #73's fully reverified private Android-debug and unsigned iOS-simulator package with exact workflow-bound provenance metadata generated by delivery_workflow_gate.py.

The staged report must be under **six hours old**, have a maximum three-minute checked window, include both anonymous private-access denials and required online status checks, and contain explicit false values for production/hardware/payment acceptance. The developer mobile package must pass all SHA-256, size, ZIP CRC, private file, source metadata and GitHub workflow identity checks. The gate now distinguishes **two separately reviewed** workflow identities: the HAS.ONE customer-only development workflow (ID 410027022) and the EV shared customer/vendor native development workflow (ID 397853920, file .github/workflows/mobile.yml). A matching shared-native developer archive can set the **shared developer bundle verified** flag, but this never counts vendor device acceptance, authenticated workflows, signed production apps or private staging connectivity.

## Operator workflow

**Critical product/endpoint limitation (verified in repository source):** The reviewed GitHub Actions workflow named Hasone customer development builds compiles the separate apps/hasone-customer Flutter project and sets EV_API_BASE_URL to https://api.hasone.io. The EV shared customer/vendor mobile client in apps/mobile is a different project with a separate mobile workflow. Consequently, passing this source-alignment gate **does not establish** that the HAS.ONE customer debug/simulator binaries connect to the private ev-staging host on loopback port 8443, or that the shared vendor Android/iOS apps are built, signed or installed. The JSON summary explicitly reports mobile backend-origin match, authenticated native journeys, physical installation and vendor Android/iOS delivery as FALSE.

The source must have been committed and reviewed first. Do not use an earlier HAS.ONE customer developer artifact as if it were an EV Charging build from the staging commit. A failure from the source gate is a genuine **handoff blocker**, not a reason to edit a manifest, forge a SHA, reset a workflow result or weaken provenance checks.

1. On an authorized isolated staging Docker host, with verified trust in the private gateway certificate, run the read-only source-linked staging acceptance command and retain its owner-only JSON report.
2. From the same source revision, arrange for Agent 6 to build the customer Android developer APK and iOS simulator artifact through the identified reviewed GitHub Actions workflow. Retrieve run and artifact listing from GitHub API and check wrapper SHA-256 hashes; use scripts/delivery_workflow_gate.py to make the owner-only bundle. Historical debug APKs and simulator archives do **not** count as store-signed releases.
3. On an authorized machine with the two private evidence sets, use a new output filename:

    umask 077
    mkdir -p -m 700 artifacts/staging-private-evidence
    python3 scripts/delivery_source_alignment.py \
      --stage-report artifacts/staging-private-evidence/source-review-UNIQUE.json \
      --mobile-bundle artifacts/delivery/verified-dev-bundle \
      --source-sha EXACT_40_CHARACTER_REVIEWED_GIT_COMMIT \
      --output artifacts/staging-private-evidence/source-alignment-UNIQUE.json

The command **never contacts GitHub, connects to a charger, deploys, changes Docker resources, processes payments, uploads credentials, signs apps or makes external requests**. It reads only owner-only staging evidence and a developer bundle. It refuses nonexistent/old/tampered reports, an incomplete private staging checklist, different staging/mobile source revisions, unreviewed or incorrectly identified GitHub Actions artifacts, and report parents readable by others.

The new private, non-overwriting output records source SHA, SHA-256 hashes of the staging report and verified developer bundle manifest, a one-way runtime fingerprint, workflow run ID and timestamp, with explicit FALSE for independently authenticated GitHub snapshot, Android/iOS device/store signing, live hardware, real money and customer/production acceptance. **It is only an unsigned operator-provided evidence consistency check.** It does not independently authenticate GitHub snapshots, prove binary reproducibility, or bind the local-only synthetic demonstration to deployed staging.

If this tool cannot pass, stage/mobile customer handoff **must remain incomplete**. Agent 4 controls source integration; Agent 6 owns signing/release; Agent 9 owns device and operational QA. Physical Teltonika/OCPP, OCPI partners, real payment processing, disaster recovery and customer contractual acceptance require additional independent evidence and explicit approvals.
