# Administrator provider-dispute deadline triage

A private authenticated GET /commercial/external-disputes/deadline-queue?window_hours=48&per_page=20 joins existing canonical provider disputes to captured invoice identities. Administrator web session only; vendor and customer roles get HTTP 403, and the existing Admin personal-token gate continues to prevent privileged native access. Window is 0–168 hours, each page has 1–25 rows. Queries select evidence-needed disputes whose deadlines are inside the requested horizon (including already overdue), unresolved evidence submissions (sending or uncertain), and lost disputes requiring reviewed financial resolution regardless of due date.

Each read-only row reports canonical invoice/currency/minor precision, disputed amount, provider-observed timestamp, deadline, current status, hold state, urgency, and whether provider observation is older than 24 hours. Explicit real_money_moved:false and provider_actions_performed:false disclose limits. Provider charge/intent references, encrypted evidence and payment secrets are excluded. A stale provider observation must be independently verified before acting; a queue read never polls external providers, creates a draft, retries or submits evidence, issues refund, modifies ledger or changes a settlement hold.

The existing English/Arabic finance dispute workspace exposes an Admin-only "Review evidence deadlines" page, displays urgency and stale-source notices, and opens the existing authorized dispute review. Existing evidence-submission deadlines and leases are preserved; this queue does not bypass them.

Feature regression tests cover time windows, Admin-only access, filtering, malformed bounds, lost held disputes, no provider identity leakage and no new refunds or finance-event records. This uses Stripe TEST contract records, not verified merchant payouts or production financial acceptance. Partial toward original dispute evidence/deadline requirements 3.5.8 and 7.3.9; neither atom is fully complete.

The queue applies an explicit urgency and NULL-deadline ordering policy because SQLite and PostgreSQL differ in default NULL sort position. Live evidence-needed disputes with actual deadlines sort first, then held/lost financial resolutions, then uncertain evidence without active deadlines. A two-dispute pagination regression proves the ordering across the shared query rather than trusting driver defaults.
