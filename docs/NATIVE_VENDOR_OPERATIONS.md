# Native company, KYC, staff and inventory operations

Canonical Flutter extends the existing Laravel vendor module; there is no second company, permission, charger or financial state machine. Customer/vendor Account → Company inventory supports company creation, scoped company management, private evidence and review history, explicit submission, staff invitations/consent/revocation, owned-catalog station selection and site/charger/connector creation. Existing topology, maintenance, admission, pricing and charging interfaces remain. Super Admin review stays on web; no Admin mobile is added.

## Workflows and authority

Owners may edit draft/changes-requested/rejected details; submitted/approved/suspended details remain locked. The license number is never returned: an empty optional edit field retains it. Submission readiness comes from the server's current license/evidence/state checks, not the phone clock. Staff with company-read permission see basic metadata, without evidence, review or owner controls. Current server permissions and operational gates still apply to every request even if a screen is stale. Returning from inventory refreshes the authenticated account so an approved customer's vendor role becomes visible.

KYC selection is PDF/PNG/JPEG, one file up to5 MiB. The client checks size before reading, reads a bounded stream and uses a fixed upload filename; the backend remains authoritative for MIME/state/ownership. Multipart and private binary reads reuse the canonical CSRF/cookie/TLS/origin/session-epoch pipeline, refuse redirects and bound responses. Encrypted server storage and private paths remain unchanged. Local PHP and staging image settings now match Laravel's existing5 MiB contract (6 MiB multipart envelope); the development start script only upgrades this checkout's disposable bind-mounted PHP runner, preserving data/keys.

Images and PDFs preview in-app, without exporting or following document links. PDF data loads from memory through pinned pdfrx2.2.24/PDFium; images use bounded decode sizing and evict their scoped cache. Preview hides when the application becomes inactive and requires reopening. Picker-owned temporary caches are cleaned on a best-effort basis; original user files are not deleted. No secure-memory erasure, screenshot prevention, document malware certification or legal identity acceptance is claimed. Privacy/retention and native dependency security review remain release gates.

Approved inventory writers can create sites and select only currently offered owned/unlinked catalog stations; the canonical station supplies its ID/coordinates. Charger sources remain discovery/simulator/direct-unverified/partner-unverified; creating metadata never enables hardware remote control. Connector numbering/type/power validation, company approval/license and lineage remain server-enforced. Lists/forms inherit Light/Dark/System, EN/AR/RTL, accessible Material semantics and scrolling.

## Durable creation and staff consent API

Company, site, charger, connector and evidence POSTs now accept optional UUID `idempotency_key`. Existing keyless requests retain their contract. Current web forms and Flutter use a stable form-owned key. `vendor_creation_receipts` contains only a user-scoped request hash, server scope, secret-keyed payload fingerprint and canonical entity ID; it stores no license/document payload. Current and retained previous application keys support fingerprint verification during key rotation. A competing insert waits on the unique receipt and transaction; the existing model/audit is created once. Changed payload/scope conflicts. Current ownership/permissions/operational state are checked before replay. SQLite/PostgreSQL prevent rewriting/deleting completed receipts. No financial tables or posting rules change.

After an uncertain response the native form disables writes and offers authoritative record review, retaining no automatic mutation retry. A known validation rejection remains editable. Canonical lists/status refresh after successful actions. Identity expiry clears private screens; late upload/download bodies are fenced after logout. Client data never grants authority.

**Staff acceptance contract:** POST `vendor-ops/staff-invitations/{id}/accept` now requires `expected_version` from the currently displayed invitation. Revocation and re-invitation advance `invitation_version`; re-invitation clears `accepted_at`. The row lock rejects old consent against changed scopes. Active replay at the same version is idempotent. Existing active memberships are retained; a null historical `accepted_at` is not invented evidence. Current web/native clients ship the new field together; old unversioned clients fail safely with422 and must refresh/upgrade. The invitation response remains generic for account eligibility and does not claim email delivery. Changing active scopes requires revoke/reinvite/fresh consent.

Company GET adds owner/Admin-only `submission_readiness` (`editable`, `license_valid`, `trade_license_present`); other scoped staff receive null. This hint never replaces the submission transaction's rechecks.

Apply `2026_11_02_000001_create_vendor_creation_receipts.php` before updated clients/workers. Its populated non-testing downgrade refuses to discard creation or renewed/accepted staff-consent records. Preserve encrypted evidence, application encryption/current+previous keys and DB backups together. An abruptly terminated upload can leave an unreferenced encrypted storage file; storage reconciliation/retention remains an operational task, never a reason to delete evidence indiscriminately.
