# Saved authorizations and recurring subscription collection

Development contract: Stripe **test mode only**. Local HTTP fakes and independently executed PostgreSQL workers verify the software contract; no merchant, physical-device, live-card or regulatory acceptance is implied. Production refuses these adapters. The original platform scope remains required.

## Canonical ownership and money boundary

`PaymentMandates` binds a durable account UUID, provider Customer, hosted Checkout setup Session, succeeded off-session SetupIntent and owned PaymentMethod. Only authenticated provider GET evidence activates a mandate. Neither a return redirect nor a client PaymentMethod ID is proof. Enrollment prepares its identity and a short lease before the outbound call; a lost acknowledgment remains inspectable with that identity. Another key cannot replace an unresolved enrollment. Provider search/list recovery requires one match and an exhausted result page.

Opaque provider references are encrypted with Laravel's application key; public responses contain masked brand/last-four/expiry, consent dates and versions. No PAN, CVV, client secret or raw provider body is stored. Keep application keys and database backups protected together. The provider hosts card entry. Consent defaults to version `recurring-v1` and365 days; both current version and expiry are enforced again at authorization/capture. Card expiry is enforced at the calendar-month boundary. Default selection uses the account version; revocation uses the method version. Immediate local revocation also disables and versions linked collection policies; provider detachment is an explicit separate reconciliation operation. Old completed enrollment callbacks cannot reactivate consent. Re-enrollment of a revoked method waits for confirmed detachment.

`SubscriptionCollections` is bounded orchestration over **existing** `SubscriptionService`, `SubscriptionGateway`, `PaymentRecovery`, immutable invoices/receipts/credits and journals. It creates no alternative balance, invoice or ledger. A verified method and explicit per-subscription policy are required; choosing a default method alone does not enable collection. Each invoice has one durable collection job. Checkout creation/attempt identity and its job link commit atomically. User/subscription locks, checkout locks, provider idempotency keys and invoice-wide unresolved-operation holds prevent competing collection. Future, cancelled, end-of-period-cancelled, zero-price, settled or non-next-cycle invoices cannot initiate collection.

Successful manual capture posts the canonical receipt and entitlements once. Recoverable `insufficient_funds`/`processing_error` declines get bounded retry intervals from configuration (default1/3/7 days **after the preceding attempt**, at most three retries). Other declines stop. Fresh explicit consent may resume a definitively failed/cancelled job, preserving old checkouts and operation identities. Changing a key or policy never bypasses an unresolved operation. A changed policy cancels an uncaptured prior checkout before attempting the newly authorized method. Unknown outcomes use authenticated GET reconciliation before any further mutation; no replacement authorization is issued on an ambiguous/empty search. A worker killed after provider acceptance is recoverable with its committed operation metadata and the same checkout.

SCA authenticates the **existing** PaymentIntent, uses the existing durable recovery mechanism, and returns only an allowlisted HTTPS provider redirect. Provider SDK-only actions are explicitly reported unsupported by this hosted client; do not start a replacement payment. Authenticated inspection or a verified webhook must establish authorization/capture before funds or entitlements are posted. A failed SCA grants no entitlement. Signed enrollment events are session-bound and replay-safe; signed payment events additionally verify the customer on saved-method checkouts. Historical payment evidence remains reconcilable after consent revocation.

Existing immutable day1/3/7 in-app reminders are preserved. Reminder screens themselves do not initiate collection. External email/SMS/push delivery remains a separate adapter requirement.

## Configuration and operation

Use `services/business-api/.env.example`; leave collection disabled by default. For an authorized sandbox configure `PAYMENT_PROVIDER=stripe_test`, `STRIPE_TEST_SECRET` (`sk_test_…` only), `STRIPE_TEST_WEBHOOK_SECRET`, an operator-controlled HTTPS `PAYMENT_HOSTED_RETURN_URL`, and explicitly enable `SUBSCRIPTION_COLLECTION_ENABLED=true`. Never place these secrets in Flutter, browser bundles, docs or logs. Provider API endpoint and version remain fixed; redirects are disabled on server HTTP requests. Only `checkout.stripe.com` and `hooks.stripe.com` HTTPS action links are accepted by the clients.

Run migrations, then the existing Laravel scheduler. `commercial:collect-subscriptions --limit=100` runs every minute when enabled, with a scheduler overlap lock; database locks/leases also protect independent workers. Limits must be1..1000. Retry configuration is validated and bounded to1..5 intervals of1..30 days. Existing subscription lifecycle, read-only payment recovery and in-app dunning tasks retain their jobs. Pause collection before configuration/key changes; reconcile outstanding operations using their original provider before switching configurations. Scheduler overlap requires a shared cache in a multi-node deployment; DB leases remain the authoritative operation fence.

Migration `2026_10_31_000001_create_recurring_payment_authorizations.php` is additive to existing gateway rows; legacy checkouts retain their identity/fingerprints. It adds encrypted reference/consent tables, collection policies/jobs and append-only audit events. A populated non-testing downgrade refuses to discard consent history. Back up first; do not delete financial/audit rows to make rollback succeed. Production release, live-mode provider adaptation, PCI/privacy assessment, merchant acceptance and restore testing remain gates.

## Authenticated API

Cookie web/native and existing Sanctum API routes share these contracts. Existing authentication, CSRF and production rate limits remain enabled. Lists use Laravel pagination (`page`,25 rows); private API responses are no-store. IDs are local scoped IDs, never provider proof.

| Method     | Relative endpoint                                       | Input / behavior                                                                                       |
| ---------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| GET        | `commercial/payment-methods`                            | `methods` page plus default ID/account version, consent version and hosted/collection capability flags |
| GET / POST | `commercial/payment-enrollments`                        | List; create with accepted `consent`, current `consent_version`, stable `idempotency_key`              |
| POST       | `commercial/payment-enrollments/{id}/inspect`           | Authoritative read/recovery; may return transient hosted URL                                           |
| POST       | `commercial/payment-methods/{id}/default`               | `expected_version` of account                                                                          |
| DELETE     | `commercial/payment-methods/{id}`                       | `expected_version` of method; immediate local revocation                                               |
| POST       | `commercial/payment-methods/{id}/detach`                | Reconcile explicit provider removal of a revoked method                                                |
| GET        | `commercial/recurring-subscriptions`                    | Owned subscriptions with policy and sanitized latest collection status                                 |
| PUT        | `commercial/subscriptions/{id}/collection-policy`       | `enabled`, `expected_version`; enabling also requires owned `mandate_id` and accepted `consent`        |
| POST       | `commercial/subscription-checkouts/{id}/authentication` | Explicit action/inspection on the existing PaymentIntent; no client credentials                        |
| GET        | `commercial/recurring-events`                           | Owned immutable consent/collection history                                                             |

Stateless signed provider callback: POST `/api/payment-enrollments/stripe-test/webhook`; verified timestamp/HMAC, event/mode/session identity and authenticated provider inspection. The existing subscription-payment webhook continues to own payment facts. Return URLs never grant payment authority.

## Clients and verification

Customer/vendor web Finance → Recurring payments and Flutter Account → Saved payment authorizations expose hosted enrollment, inspection, default/revoke/remove, subscription policies, collection failures/SCA, consent audit and canonical invoice/receipt/credit history. Existing recovery/invoice views remain available. Both clients preserve a stable enrollment key after uncertain responses and require deliberate refresh/inspection. They never automatically replay mutations, accept card fields or store provider links in preferences. Async response fences, expiry handling and logout remove private data; EN/AR, existing theme preferences and RTL are retained. Flutter uses pinned `url_launcher6.3.2` to open the allowlisted provider website outside the application.
